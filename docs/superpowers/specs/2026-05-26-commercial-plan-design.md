# GT 商业化改造设计 — 扩展 AuthAPI 方案

## Context

当前 GT 客户端只要拿到 secret 就能配置任意子域名和端口转发，缺乏套餐/配额管控。本设计通过扩展现有 AuthAPI 接口，引入订阅制套餐体系，实现按套餐限制子域名数、隧道数、带宽、并发连接数等资源。

## 商业模式

- **SaaS 平台**：运营中心化服务，用户注册、选套餐、自助开隧道
- **订阅制优先**：免费/基础/专业/企业套餐，按月/年付费，后续扩展按量计费
- **第三方 Auth**：用户注册登录借用 Casdoor 等第三方服务，聚焦做隧道管控和计费
- **全量管控**：子域名、端口/隧道数、带宽/流量、并发连接数

## 整体架构

```
┌─────────────┐     ┌──────────────────┐     ┌─────────────────┐
│  GT Client  │────▶│   GT Server      │────▶│  AuthAPI 服务    │
│  (桌面/CLI) │     │                  │     │  (需新建)        │
└─────────────┘     │  1. 握手时调      │     │                 │
                    │     AuthAPI 验证   │     │  - 用户注册/登录 │
                    │  2. 获取配额       │     │  - 第三方 Auth   │
                    │  3. 按配额限制资源  │     │  - 套餐管理      │
                    │  4. 用量上报       │     │  - 支付集成      │
                    └──────────────────┘     │  - 配额下发      │
                                             └─────────────────┘
```

### 职责划分

| 组件 | 职责 |
|------|------|
| **GT Server** | 专注隧道转发。连接握手时调 AuthAPI，获取配额后本地执行限制。定期上报用量。 |
| **AuthAPI 服务**（需新建） | 用户管理、套餐定义、配额下发、用量统计、支付回调。可用 Casdoor 做登录，自己写配额+计费层。 |
| **GT Client** | 不变，仍传 id/secret 和隧道配置。 |

## 现有可复用资源

已有功能可复用：
- **JWT 认证体系**：HS256 签名、token 刷新、临时 key 机制
- **用户管理页面**：用户 CRUD、per-user TCP/Host/Speed/Connections 限制
- **配置管理**：运行配置读写、在线保存
- **连接监控**：实时连接池状态、外部连接列表
- **系统监控**：CPU/内存/磁盘仪表盘

### 需要新增的部分

在现有 Web 管理中扩展：
- 套餐定义/管理页面
- 用户-套餐绑定管理
- 用量统计仪表盘（流量、连接时长等）
- AuthAPI 对接配置页面

## 核心改动

### 1. 扩展 AuthAPI 返回结构

当前 AuthAPI 只做验证（返回 true/false），扩展为返回配额信息：

```json
{
  "allowed": true,
  "user_id": "user123",
  "plan": "pro",
  "quotas": {
    "host_number": 10,
    "tcp_number": 20,
    "host_regex": ["^[a-z0-9-]+$"],
    "host_with_id": true,
    "speed": 10485760,
    "connections": 100,
    "monthly_traffic_mb": 102400,
    "tcp_ranges": ["10000-60000"]
  }
}
```

### 2. GT Server 端改动

- **扩展 `authUserWithAPI()`**：解析返回的配额信息，构造完整的 `user` 结构体
- **配额缓存**：本地缓存用户配额，避免每次连接都调 AuthAPI（TTL 5 分钟）
- **用量上报**：定时（如每分钟）向 AuthAPI 上报用户的连接数、流量等用量数据
- **流量计费钩子**：在数据转发路径上统计流量，超限后限速或断开

### 3. AuthAPI 服务（新建）

轻量 Go/Node 服务，核心接口：

| 接口 | 用途 |
|------|------|
| `POST /auth/verify` | 验证用户并返回配额（替代现有 AuthAPI） |
| `POST /usage/report` | 接收 GT Server 的用量上报 |
| `GET /admin/plans` | 套餐 CRUD |
| `GET /admin/users` | 用户-套餐管理 |
| `POST /payment/callback` | 支付回调（对接支付宝/微信/Stripe） |

### 4. 套餐模型

```
┌─────────────────────────────────────────────────┐
│  Free         │  Basic    │  Pro       │  Enterprise │
├───────────────┼───────────┼────────────┼─────────────┤
│ 1 子域名      │ 5 子域名  │ 20 子域名   │ 无限        │
│ 1 TCP 隧道    │ 5 TCP     │ 20 TCP     │ 无限        │
│ 1 Mbps        │ 10 Mbps   │ 50 Mbps    │ 无限        │
│ 5 并发连接    │ 50 连接   │ 500 连接   │ 无限        │
│ 1 GB/月       │ 100 GB/月 │ 1 TB/月    │ 无限        │
│ ID 前缀强制   │ ID 前缀   │ 自定义     │ 自定义      │
└───────────────┴───────────┴────────────┴─────────────┘
```

## 验证方案

1. 启动 AuthAPI mock 服务，返回不同套餐的配额
2. 启动 GT Server，配置 AuthAPI 地址
3. 用不同套餐用户连接，验证：
   - 超出子域名数限制时被拒绝
   - 超出 TCP 隧道数限制时被拒绝
   - 超出并发连接数时被拒绝
   - 限速生效
4. 检查用量上报数据是否正确

## 实施优先级

1. **P0**：扩展 AuthAPI 返回结构 + GT Server 配额执行逻辑
2. **P1**：套餐管理后台页面（复用现有 Web 管理）
3. **P2**：用量上报 + 统计仪表盘
4. **P3**：支付集成
